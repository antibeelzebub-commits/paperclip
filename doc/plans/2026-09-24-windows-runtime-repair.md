# Windows runtime repair and source-managed deployment

Date: 2026-09-24. Revision: 2. Status: revised after independent review; delta review pending. This status describes the submitted review input; the separate review receipt records the final gate decision against its exact hash.

## Outcome and scope

Make Windows execution ownership and pre-provider review waits reliable, then reconcile only proven affected task state. Preserve company boundaries, single-assignee document writes, review/approval gates, budgets, explicit pauses, cancellation evidence, and unknown-action holds.

This document is a repair plan, not a deployment approval or a claim that repairs passed. The source fork and checkout are prepared. The existing deployed package remains unchanged. Application tests, source-to-deployment parity, restore rehearsal, and repair canaries are NOT_TESTED.

## Evidence and upstream position

The investigation found three distinct failure classes. Database responsiveness and a healthy HTTP endpoint do not establish task progress.

1. A task's child assignee attempted to update its parent's plan document. The document endpoint rejected it with `403: Agent cannot mutate another agent's issue`. Provider success did not mean the document revision was saved. This is an ownership mismatch, not a reason to widen authorization.
2. Legacy runs cancelled with `issue_continuation_waiting_on_review`, null start/PID metadata, and no recorded `adapter.invoke` can become persistent `legacy_execution_requires_reconciliation` holds. A resolved recovery row still blocks when its evidence retains `automaticRecovery.replay=blocked`.
3. A Windows PID was reused by a different process. `Get-Process.StartTime` was unreadable, while CIM supplied a creation time incompatible with the stored provider identity. The continuation path treated uncertain identity as a definitely active provider.

Public references: [issue #13640](https://github.com/paperclipai/paperclip/issues/13640), [PR #13150](https://github.com/paperclipai/paperclip/pull/13150), and [stable release](https://github.com/paperclipai/paperclip/releases/tag/v2026.916.1). At inspection, PR #13150 was open and unmerged at `f2ca15db4cb314e44187e3c01f1d967583910ee1`. It supplies a narrow pending-review reconciliation proposal, not complete prevention or a qualified Windows deployment. Recheck its status before adopting code; preserve attribution and prefer an equivalent merged fix when available. Do not execute database workarounds from issue comments.

## Repair A: Windows process identity

Primary paths: `server/src/services/hot-restart.ts`, `server/src/services/conversation-continuation.ts`, and `server/src/services/execution-recovery-resolution.ts`. The latter's validator separately tests bare PID/group liveness and can reject reconciliation after a continuation check succeeds. Inventory all ownership/stop/reconciliation consumers, not only existing `readProcessStartedAt` callers, and use a consistent evidence contract. Keep destructive stop paths separately guarded.

1. Inventory every writer of `processStartedAt`, `processPid`, and `processGroupId` on the release base and in the deployed dependency patches. Establish whether persisted timestamps are OS creation times or approximate spawn times. Only compare compatible, proven OS identity sources. Historical rows with uncertain timestamp provenance remain `unknown`; do not add a broad tolerance to turn an approximate timestamp into proof. Establish whether process groups are populated on Windows and verify native Node/libuv negative-PID behavior. POSIX group semantics must not be assumed on Windows; unsupported or ambiguous group ownership remains held until a supported, separately verified ownership source settles it.
2. Use a single hidden, noninteractive Windows shell invocation that tries `Get-Process` and then read-only `Get-CimInstance Win32_Process` creation time when needed, returning a small structured observation. Validate `Number.isSafeInteger(pid) && pid > 0` before forming the fixed script. Distinguish missing shell from lookup denial/failure; use an alternate shell only for shell unavailability. Set bounded output and a shared total deadline based on measured cold-start latency under the normal scheduled-task account. No WMI service changes or administrator requirement. Normalize compatible persisted and observed values to UTC using identical floor-to-millisecond rules. Distinguish `matching`, `mismatched`, `absent`, and `unknown` identity. Access denial, timeout, malformed output, missing expected identity, and conflicting observations are `unknown`, not proof that execution stopped.
3. A proven mismatched PID must not keep the old PID ownership active. A missing or mismatched root does not prove child/group, remote execution, controller lease, or environment cleanup is settled. Check the existing independent ownership gates. Never signal a reused PID or an unproven process group.
4. Preserve the blocker when ownership remains unknown, but describe the uncertainty accurately; never tell the operator to signal a mismatched or unverified PID. A live matching owner stays blocked. Keep company scope and current pause/review/budget gates. Run shell probes outside row-locking transactions. Only a proven absence or incompatible OS identity can settle the old root's ownership. Under the existing task/dispatch lock, compare-and-swap against the same run identity/version and recheck all independent authority fields; restart evaluation if state changed. Never hold a database lock across a shell probe. Identity observations are not transferable authorization to kill a process later.
5. Keep non-Windows behavior unchanged. Bound aggregate probe work across multiple candidate runs so a request cannot stall for an unbounded number of shell probes.

Required checks: matching owner; approximate or unknown persisted timestamp source; reused PID; missing PID; access denial in both probes; null/invalid timestamps; milliseconds/microseconds normalization; DST fall-back-hour conversion; process exit/reuse between observations; held/failed-cleanup lease; live controller; child/group still active; native Windows negative-PID behavior; repeated reads; hidden-window execution and measured cold-start latency on native Windows; no signal sent; no probe while a row lock is held. Verify all existing hot-restart consumers still fail safely.

## Repair B: pre-provider review cancellation

Primary paths: `server/src/services/legacy-execution-recovery.ts`, `server/src/services/heartbeat.ts`, `server/src/services/execution-recovery-resolution.ts`, `server/src/services/recovery/service.ts`, and `server/src/routes/issues.ts`.

1. First write the failing end-to-end regression on `dffc2b3`, then run the same case on `d554c478` and `f55759942`. The specification already describes review-wait disposition repair; locate its implementation and determine whether an upstream fix already satisfies the case. Prefer porting that fix with attribution over duplicating it. Trace the exact cancellation write and dispatch boundary on the selected source base. Add durable, server-produced pre-dispatch evidence only if still required at the branch that cancels before any provider invocation. Do not exempt an error-code string alone or trust client-supplied `providerWorkStarted=false`.
2. Under the existing task/run locking and compare-and-swap rules, classify that verified pre-provider review wait as a governed wait/disposition-repair condition. Preserve the real review stage and participant. If there is no current typed wait target, retain the existing bounded disposition-repair policy and its durable attempt ceiling; do not create an endless retry. After classification, require one authoritative next-action path: a typed wait, a scheduled disposition repair with a due time, or board escalation. Other evidence may coexist, but it must not create duplicate action owners or leave an `in_review` task stranded.
3. Update every path that creates or reconstructs a legacy recovery hold, including startup, terminalization, and periodic stranded-work sweeps. Verify classifier ordering so an attempt counter cannot turn proven pre-provider work into an unknown-action hold. Genuine invoked/interrupted work and incomplete evidence remain held.
4. For historical rows, null `startedAt`/PID and absence of an event are corroborating evidence only. Verify the exact pre-dispatch code path, complete event lineage/retention, terminal reason, no controller/remote dispatch/lease activity, and no provider-side effects. Missing evidence remains blocked. Do not infer never-started from a pruned log.
5. Evaluate the pinned upstream reconciliation proposal against this source base. PR #13150 addresses `stale_queued_run_gate` / `execution_reconciliation_required` and manual pending-review reconciliation, not prevention of this exact review-wait trigger. Check whether its base `2a05b5ed3457ea33efd6895520447d1d97fe98d8` is an ancestor of the release base. Semantically port any useful change: its fifth `markExecutionReconciliation` argument (`deliveryMode`) conflicts with master's `deliveryOwner` / `chat_failed_run_retry` behavior, and it changes the return-owner guard. Test delegated delivery crossed with ordinary/review mode. Its null-start/no-event check is weaker than step 4 and must not replace the stronger evidence requirement. Preserve board-only recovery authority, company checks, reviewer, stage, return owner, and approval gates. Revalidate them in the transaction and again under the enqueue/dispatch lock. Reject stale review stages, unauthorized actors, actual starts, or unknown outcomes.
6. Reconcile every duplicate blocking recovery row for the same verified source run through the supported, audited service/API. Before removing or replacing `automaticRecovery`, record the prior evidence plus actor, time, decision and new evidence in an immutable activity/audit entry in the same transaction. Atomically record the decision before clearing the matching execution blocker. Prove a durable enqueue deduplication key shared by all recovery rows for that source run, and verify it in the real wake service rather than assuming existing coalescing suffices. Deliver at most one continuation to the current authorized participant across concurrent calls, retries and crashes between enqueue and receipt recording. Use fair ordering/backoff or escalation so repeatedly failing rows cannot starve later pending recoveries. Do not mark the business task done.

Required checks: exact review-wait error on all three bases; other queued-cancellation code; provider invoked despite null start; incomplete/pruned events; genuine failure/timeout/cancellation; quota/workspace waits; typed review target present/absent; exhausted disposition budget; pending human approval; actor/company denial; reassignment/stage change during delivery; duplicate recovery rows; concurrent resolvers; delegated delivery crossed with review mode; crash before/after decision and specifically after enqueue but before delivery receipt; repeatedly failing early rows plus later pending rows; prior-evidence audit; repeated scheduler/startup sweeps. Prove one authoritative next-action path, no duplicate provider dispatch and no return of the false hold.

## Task-state correction after qualification

Keep this separate from runtime code repair. Prepare the exact proposed writer, document body/provenance and API effects for the owner first. Use existing explicit authorization when it covers them; otherwise obtain the owner's bounded decision before dispatch or a business-content change. Do not silently copy a child agent's unaccepted output or regenerate business content. Read back the target's current assignee, plan revision, active runs, hold evidence, `executionState` and explicit owner acceptance requirements. Use the Board-authorized assignment API for the intended writer with verified deferred-wake support; if absent, do not reassign until the immediate wake is separately authorized or an accepted board-authored alternative is selected. Read back `executionState` and return owner before and after. Preserve the independent recovery hold until separately reconciled. Do not change global document authorization. Revalidate the revision and writer immediately before the document write; require exact revision/body readback and retain the human plan-acceptance step. A successful provider turn alone never proves success. Prevent recurrence operationally by checking document-writer authority before delegation and requiring write receipts/readback before declaring the deliverable complete. The product's ability to report a successful turn after a rejected write remains an explicit open risk, not fixed by these two runtime patches.

Do not broadly release older failed/timed-out runs, sweep deferred wakes, enable timers, switch engines, or dispatch business work as a health test. The earlier model/engine mismatch was already repaired; retain that qualified route and verify its real executable/model during acceptance.

## Longer-term maintenance

Keep a small fork patch set and retire each patch only after an upstream equivalent passes the same regression tests. Prepare public contributions from generic synthetic cases; publish no local issue identifiers or logs. Review upstream updates on demand, build a separate candidate, and admit it through this same qualification process. Do not run production from a mutable checkout or auto-update to master.

Add bounded local operational logging only through reviewed existing configuration: startup/recovery readiness, process-probe result class, blocking reason and database error diagnostics. Set retention and redaction; do not log SQL parameter values, credentials or full prompts, and do not enable a remote telemetry sink as part of this repair. Log rotation and a harmless local failure probe must be verified before relying on the logs. This is a planned improvement, not an active monitor.
